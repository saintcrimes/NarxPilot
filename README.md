# NarxPilot

B2B-закупки точных SKU смартфонов в Ташкенте и аналитика зарегистрированных событий. Интерфейс на русском, деньги Decimal/NUMERIC в строках JSON, хранение времени UTC, отчётные дни Asia/Tashkent.

**Статус:** продолжение исходного прототипа, не пересоздание. Linux CI прошёл для версии, указанной в [отчёте проверки](docs/VERIFICATION.md): lint, типы, unit/integration, Next.js build, Docker-сборки, запуск Compose, Caddy и 6 desktop/mobile E2E, включая весь цикл закупки до аналитики. Настоящий package-lock.json сохранён в репозитории. Локальные npm/Docker ограничения сохраняются. По запросу владельца демонстрационный стенд открыт для всех без браузерного пароля; данные синтетические. Реальные организации требуют production-аутентификации.

## Сервер и домен

Главная `/` представляет продукт и планируемую бизнес-модель. «Попробовать демо» открывает готовый аккаунт покупателя одним нажатием; «Посмотреть аналитику» ведёт к графикам из событий демобазы. `/register` создаёт пользователя и отдельную организацию покупателя/поставщика, `/login` выполняет вход по email и паролю. Пароли хранятся как PBKDF2-SHA256 с индивидуальной солью; миграция 004 добавляет приватную таблицу учётных данных. Подтверждение email, восстановление пароля и приглашения пока не реализованы.

Фирменные PNG из `design/` используются в тёмной фиолетовой теме. Анимации отключаются при системном `prefers-reduced-motion`. В аналитике есть быстрый выбор сценариев seed: стабильный iPhone, снижение цены, снижение продаж при прежней цене и отсутствие сделок. Снижение количества 1 000 → 500 означает −50% объёма; при прежней цене изменение цены равно 0%.

На Ubuntu/Debian-сервере после настройки DNS A-записи домена и открытия TCP 80/443:

```bash
curl -fsSL https://raw.githubusercontent.com/saintcrimes/NarxPilot/main/deploy/install.sh | sudo bash
```

Установщик клонирует проект в `/opt/narxpilot`, настраивает **narxpilot.software-engineer.online**, HTTPS, серверные секреты, миграции, demo seed и healthchecks. Демо доступно публично без окна HTTP Basic Auth. Ваш локальный `.env` не попадает в GitHub: API-ключ задаётся отдельно на сервере. [Полная инструкция, обновление и backup](docs/DEPLOYMENT.md).

## Что есть в коде

- Каталог десяти точных SKU, поиск, сравнение количества/склада/свежести, итог товара + доставка один раз + сборы. Неизвестная доставка даёт `null`.
- Заявка → версия котировки поставщика → согласие покупателя → атомарный резерв → отгрузка → приёмка. Снимок условий, проверка ролей и участников, идемпотентность, журнал и outbox.
- Отмена до отгрузки, истечение резерва, спор до приёмки, запрос/подтверждение возврата. Дефектный возврат попадает в карантин.
- Кабинет поставщика: свои предложения, новая версия/новое предложение существующего SKU, приход/списание/сверка/перемещение, CSV с предварительной проверкой. Внешняя продажа отмечается отдельно и не становится подтверждённой сделкой индекса.
- Аналитика из событий: медиана сделок и предложений раздельно, VWAP, нетто-объём, запас, два полных 7-дневных окна, качество и подавление малых групп. Worker пересчитывает историю при возвратах и повторной доставке; в полночь обновляет окна.
- Избранное, пороги опубликованной цены и уведомления внутри приложения.
- Независимые аналитические пояснения: шаблон без ключа либо серверный OpenAI provider с проверкой утверждений/metric_id. Реальный provider не проверялся. Экспериментальная ML-модель пока **не обучена и выключена**; её отсутствие не отключает аналитику.
- Дополнительная «Помощь по NarxPilot»: локальная справка по умолчанию и необязательный серверный поставщик Bro24 по примеру запроса из `bro24.md`. `CHATBOT_ENABLED=false` и `CHATBOT_PROVIDER=local` по умолчанию. Схема ответа внешнего сервиса ещё не предоставлена; живое подключение не проверено. Аналитические AI-пояснения остаются независимыми. Старый документ интеграции сохранён как архив и не заменяет контракт.

## Стек

Next.js 16.2.1 / React 19.2.4 / TypeScript 5.9.3; PostgreSQL 18; существующий node-postgres слой и SQL-миграции; Python 3.12 / asyncpg 0.32.0. SVG-графики получают только сохранённые агрегаты, без браузерной генерации истории. [Решения и допущения](docs/DECISIONS.md).

Прямые npm-версии зафиксированы в package.json, дерево зависимостей — в настоящем package-lock.json, созданном npm в GitHub CI. Docker использует `npm ci`. Python-зависимости перечислены с точными версиями в `worker/requirements.lock`. Обе закреплённые контейнерные сборки прошли в CI.

## Локальный запуск с Docker

Нужны Node.js 22.12+ (до 25), npm и работающий Docker Compose. Внешние AI-ключи не нужны.

```sh
npm ci
npm run setup:env
docker compose up --build -d
```

`npm ci` использует сохранённый lockfile. `setup:env` генерирует локальные секреты и никогда не перезаписывает существующий `.env`. Compose запускает PostgreSQL, миграции, отдельные роли web/worker, идемпотентный seed при DEMO_MODE, web и worker. Web доступен по `http://localhost:3000`; PostgreSQL наружу не публикуется.

Для диагностики:

```sh
docker compose ps
docker compose logs --tail=80 web worker migrate
docker compose exec web node -e "fetch('http://localhost:3000/api/health/ready').then(r=>console.log(r.status))"
```

Созданы healthchecks процесса, схемы/происхождения базы и heartbeat worker. Если worker недоступен, покупки продолжают сохраняться; интерфейс показывает очередь и время последнего расчёта.

## Демо-путь

1. Выберите покупателя «Магазин „Орион“» в верхнем списке.
2. Найдите `iPhone 15 128`, откройте сравнение пяти поставщиков и задайте 5 шт. При желании явно сохраните сопоставимую альтернативу; без неё экономия не рассчитывается.
3. Отправьте заявку выбранному поставщику. В заказе видны его название и сохранённые условия.
4. Переключитесь на соответствующего поставщика и нажмите «Подтвердить условия».
5. Вернитесь к покупателю, проверьте новую котировку и согласитесь с её версией — появится резерв.
6. Поставщик подтверждает отгрузку; покупатель подтверждает приёмку.
7. Откройте аналитику. Worker увеличит версию снимка. Один заказ не раскрывается публично при малой группе; поставщик видит его в «Моих данных».

Все поставщики, цены и 180 дней истории — синтетические. Seed: 10 SKU, 5 поставщиков, 2 локации; историческая часть привязана к `DEMO_ANCHOR_DATE=2026-10-31`. Текущая свежесть предложений использует часы запуска. Данные demo и live разделены физической базой и проверяются триггерами. Быстрая смена аккаунта — только для локальной демобазы.

## Локальная разработка без контейнеров

Создайте отдельную PostgreSQL-базу `narxpilot_demo`. В `.env` задайте рабочие `MIGRATION_DATABASE_URL` для владельца, `DATABASE_URL` для web и `WORKER_DATABASE_URL` для worker; роли создаёт `db:grants`. Порт/пароль должны соответствовать вашему серверу. Скрипт grants принимает сгенерированные пароли из латинских букв/цифр длиной от 32 символов.

```sh
npm ci
npm run db:migrate
npm run db:grants
npm run db:seed:demo
npm run dev
```

В отдельном терминале Python 3.12:

```sh
python -m venv .venv
# Активируйте .venv и передайте DEMO_MODE, WORKER_DATABASE_URL из .env в окружение.
python -m pip install -r worker/requirements.lock
python -m worker.main
```

Python worker не читает `.env` автоматически; Compose передаёт его через env_file. Для локального POSIX shell можно экспортировать переменные `set -a; . ./.env; set +a`. В PowerShell задайте `$env:DEMO_MODE='true'` и `$env:WORKER_DATABASE_URL` соответствующим значением. Секреты не публикуйте.

## Проверки

Node-интеграционные тесты требуют **пустую отдельную** базу `narxpilot_test_web`, в которую seed создаёт fixtures. Python DB-тесты используют отдельную `narxpilot_test_worker`; не направляйте их в demo/live. Пример переменной: `TEST_DATABASE_URL=postgresql://USER:PASSWORD@localhost:5432/narxpilot_test_web`.

```sh
npm run lint
npm run typecheck
npm run test:unit
npm run test:integration
python -m pytest worker/tests -q
npm run build
# После запуска web + worker на демобазе:
npx playwright install chromium
npm run test:e2e
```

Для Python DB-тестов переопределите TEST_DATABASE_URL на worker test-базу. Без неё DB-тесты явно пропускаются. Чистую арифметику можно проверить без pytest: `python -m unittest discover -s worker/tests -p test_analytics.py -v`.

E2E предусмотрен для desktop и mobile. Для проверки включённого локального FAQ задайте `CHATBOT_ENABLED=true`, `CHATBOT_PROVIDER=local`, перезапустите web и повторите E2E. Отсутствующий флаг и false скрывают виджет. Этот флаг никак не переключает LLM_PROVIDER/ANALYTICS_MODE. В local нет внешних запросов и постоянного хранения переписки.

## Необязательный внешний чат Bro24

`bro24.md` документирует POST `https://dashboard.bro24.uz/api/v1/public/chat` с заголовком `X-API-Key` и JSON `client_id`, `channel: "website"`, `message`. NarxPilot вызывает фиксированный адрес со своего сервера и использует HMAC-псевдоним клиента; ключ и открытые идентификаторы пользователя/организации в браузерный запрос к Bro24 не попадают. Отдельный backend чат-бота не создаётся.

Для включения нужны `CHATBOT_ENABLED=true`, `CHATBOT_PROVIDER=bro24`, серверный `BRO24_API_KEY` и `BRO24_REPLY_JSON_PATH` — явный путь к строковому ответу в JSON. **Пример ответа ещё не предоставлен: путь нужно взять из реального обезличенного ответа, а не предполагать имя поля.** Без настроек, при таймауте, ошибке сервиса или неподходящем ответе используется локальная справка. После изменения env перезапустите web.

Внешний режим передаёт текст вопроса Bro24. NarxPilot не сохраняет переписку постоянно; правила хранения внешним сервисом пока не подтверждены. Контекст продукта/база знаний на его стороне также требуют подтверждения: предоставленный пример не содержит отдельного поля контекста. Покупки и аналитика работают независимо. Живое подключение ещё не проверено; подробный контракт и границы — [docs/PRODUCT_CHATBOT.md](docs/PRODUCT_CHATBOT.md).

## Сброс и ограничения

Сброс удаляет **только явно названную синтетическую демобазу** и требует аргумента:

```sh
npm run db:reset:demo -- --confirm=narxpilot_demo
npm run db:migrate
npm run db:grants
npm run db:seed:demo
```

Скрипты миграции/seed/reset используют MIGRATION_DATABASE_URL; обычное приложение — DATABASE_URL. Для live/test reset запрещён. После перезапуска демобаза сохраняется в Docker volume. Не используйте `docker compose down -v`, если требуется сохранить закупки.

Не реализованы production-вход, реальные поставщики/внешние данные, оплата, сторонние уведомления, разрешение споров, финансовые adjustments, полноценный антифрод и ML-бэктест. Серверный стенд демонстрирует синтетические данные. До работы с реальными организациями нужны отдельные проверки безопасности, приватности, согласий и восстановления резервной копии.

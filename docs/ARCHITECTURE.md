# Архитектура и контракты

Это проектное решение команды. Стек можно адаптировать к существующему репозиторию, сохранив правила данных и проверяемость.

## 1. Компоненты

```text
Браузер: покупатель / поставщик / администратор
              |
        HTTPS + сессия
              v
Next.js / TypeScript: UI + серверные API
  | каталог | сравнение | заказы | права | помощник |
              |
              v
PostgreSQL
  transactional: организации, предложения, заказы, склады
  events: журнал бизнес-событий + outbox
  analytics: агрегаты, качество, версии прогнозов
              |
              v
Python worker
  получение событий → проверка/агрегация → сигналы
  по расписанию → необязательная модель прогноза
              |
              v
UI читает результаты через авторизованный API

Локальный FAQ-виджет → утверждённый JSON, без сети и доступа к данным
Серверный ExplanationProvider → шаблон / настроенный LLM
```

Приложение — модульный монолит с отдельным вычислительным процессом, не распределённая сеть микросервисов. PostgreSQL — источник истины. Аналитика воспроизводится из событий. Никаких графиков из локальных случайных массивов браузера.

В MVP достаточно периодического запроса результатов клиентом. Обновление «live» означает новые зарегистрированные события и время расчёта, а не гарантированный поток всех сделок рынка. WebSocket/SSE необязательны.

Next.js допускает самостоятельное размещение; официальная документация рекомендует reverse proxy при таком размещении (S7). Библиотека графиков работает в клиентском компоненте и требует соблюдения её атрибуции (S6).

Имена папок — рекомендация. Не дублировать одинаковые правила резервирования и цен на клиенте, в API и в worker: авторитетная реализация — серверный domain слой и ограничения базы.

## 3. Сущности

| Сущность | Обязательное содержание |
|---|---|
| organizations / memberships | организация, пользователь, роль, разрешения |
| products / skus | канонический товар и сопоставимый вариант |
| locations / warehouses | география и принадлежность склада |
| offers / offer_versions | SKU, поставщик, количество, цены, условия, valid_until, last_verified_at |
| inventory_balances | on_hand, reserved, версия, склад/SKU |
| reservations | количество, заказ, срок, статус, ключ идемпотентности |
| orders / order_lines | стороны, статус, снимок условий, суммы и даты |
| shipments / receipts | подтверждение отгрузки и приёмки, количество, автор |
| returns / adjustments | ссылка на исходную строку, количество/сумма, состояние, причина |
| inventory_events | приход, отгрузка, возврат, перемещение, списание, корректировка |
| business_events / outbox | событие, уникальный ID, версия, очередь обработки |
| analytics_snapshots | когорта, окно, показатели, качество, data_cutoff, version |
| forecasts | модель, горизонт, оценка/интервал, история проверки, ограничения |
| alert_rules / deliveries | условия, получатель, канал, дедупликация, согласие |
| FAQ | локальный версионируемый JSON; таблица переписки не создаётся |
| audit_log | субъект, действие, объект, результат, дата, request_id |

Ограничения: уникальный SKU канонического варианта; уникальный остаток `(warehouse_id, sku_id)`; допустимые значения количества; `reserved <= on_hand`; уникальный внешний ID в пределах источника; уникальный idempotency key в пределах организации/операции. Первичные ключи — непрогнозируемые идентификаторы, но это не замена авторизации.

`offer_version` и снимок заказа неизменяемы после принятия. Исправление создаёт новую версию. Нельзя пересчитать старый заказ по сегодняшнему прайсу.

## 4. Критический путь заказа

1. Покупатель отправляет REQUESTED с конкретным SKU, количеством и выбранным предложением.
2. Поставщик создаёт QUOTED: цена, количество, доставка, условия, срок котировки. Это ещё не продажа.
3. Покупатель подтверждает согласие. Сервер проверяет членство, версию условий, срок и количество.
4. В одной транзакции сервер блокирует соответствующий остаток либо выполняет условное атомарное обновление, проверяет `available >= quantity`, создаёт резерв и переводит заказ в RESERVED.
5. В той же транзакции записываются аудит и событие outbox. Сеть/AI/внешние API внутри этой транзакции не вызываются.
6. При отгрузке уменьшаются on_hand и reserved, резерв становится использованным. SHIPPED не является завершённой продажей для индекса.
7. При подтверждении приёмки заказ становится COMPLETED и создаётся факт сделки.
8. Worker пересчитывает затронутую когорту/дни и обновляет аналитический снимок. Клиент видит новую версию.

PostgreSQL предоставляет блокировки строк для контроля конкурентных изменений (S9). Реализация должна иметь автоматический тест: два покупателя не могут зарезервировать одну последнюю единицу. Для нескольких строк блокировки берутся в стабильном порядке; предусмотреть ограниченный повтор транзакций при конфликте.

Резерв истекает только до отгрузки. Задача истечения повторно проверяет статус в транзакции; она не должна освободить уже отправленный товар. Повторный запрос возвращает прежний результат по idempotency key, а не создаёт новую операцию.

## 5. События и обработка

Минимальные типы:

```text
OfferPublished / OfferConfirmed / OfferExpired
InventoryReceived / InventoryAdjusted / InventoryTransferred
OrderRequested / QuoteIssued / QuoteAccepted
StockReserved / ReservationReleased / ReservationExpired
OrderShipped / ReceiptAccepted / OrderDisputed
ReturnAccepted / FinancialAdjustmentAccepted
ExternalSaleReported / SourceReconciled
```

Оболочка события:

```json
{
  "event_id": "uuid",
  "schema_version": 1,
  "type": "ReceiptAccepted",
  "organization_id": "uuid",
  "aggregate_id": "order-uuid",
  "aggregate_version": 4,
  "occurred_at": "2026-10-31T08:00:00Z",
  "recorded_at": "2026-10-31T08:00:01Z",
  "source_type": "platform_order",
  "external_id": null,
  "data_origin": "synthetic",
  "payload": {
    "order_line_id": "uuid",
    "sku_id": "uuid",
    "quantity": "5",
    "unit_price_uzs": "8000000.00"
  }
}
```

В событии не хранить ненужные телефоны, переписку и адреса. Это контракт нашего приложения.

Outbox создаётся вместе с бизнес-изменением. Worker получает задания с арендой/статусом, retry и дедупликацией по event_id/версии обработчика. Разрешена доставка «как минимум один раз»; обработчик должен быть идемпотентным. Истёкшая аренда позволяет повтор после падения процесса. Не помечать событие успешно обработанным до сохранения результата.

Для MVP проще пересчитать затронутый день/когорту из авторитетных фактов, чем многократно прибавлять и вычитать дельты. Позднее событие или возврат инвалидирует старые снимки. Хранить watermarks, data_cutoff и причину пересчёта.

Ошибка аналитики не отменяет уже сохранённую сделку. UI показывает «аналитика обновляется» и дату последнего расчёта. Внешний LLM и независимый локальный FAQ не являются обязательными для оформления и приёмки заказа.

## 6. API нашего приложения

Это проектируемые маршруты NarxPilot, не существующие сторонние API.

| Метод / маршрут | Назначение |
|---|---|
| GET /api/products | канонический каталог с фильтрами |
| GET /api/skus/:id/offers | сопоставимые актуальные предложения |
| POST /api/compare | полная стоимость заданного количества |
| POST /api/orders | заявка, обязательный idempotency key |
| POST /api/orders/:id/quote | котировка поставщика своей организации |
| POST /api/orders/:id/accept | согласие покупателя и атомарный резерв |
| POST /api/orders/:id/ship | отгрузка поставщиком |
| POST /api/orders/:id/receive | подтверждение покупателем |
| POST /api/orders/:id/cancel | отмена по допустимому состоянию |
| POST /api/orders/:id/returns | создание/подтверждение возврата по правилам |
| GET /api/analytics/:skuId | агрегированный снимок и качество |
| GET /api/analytics/:skuId/series | факты/предложения/прогноз раздельно |
| POST /api/analytics/explain | пояснение разрешённых public-агрегатов; без действий с заказами |
| GET /api/health/live | процесс доступен |
| GET /api/health/ready | готовность базы/миграций |

Запросы фильтруются по правам на сервере. Нельзя доверять organization_id, присланному клиентом, без проверки membership. Для заказов авторизация проверяет и организацию, и роль стороны сделки.

Каждый аналитический ответ содержит `scope`, `cohort`, `window`, `as_of`, `data_origin`, `sample`, `quality_flags`, `metric_definitions_version`. Ошибки — стабильный code и безопасное сообщение; внутренние SQL/секреты не раскрываются.

## 7. Безопасность и приватность

Сессии HttpOnly/Secure и проверка изменяющих запросов; проверенная библиотека аутентификации вместо самодельной криптографии. Для demo переключение ролей работает только с отдельными тестовыми аккаунтами, без production-данных.

RBAC и объектные разрешения, ограничения частоты/размера запросов, валидация схем, аудит критических операций. Секреты — в переменных окружения/secret storage, не в браузере и не в репозитории. Для БД — отдельные минимальные права web/worker; worker не должен менять чужие роли или цены.

CSV: предварительный просмотр, ограничения числа строк/размера, отчёт ошибок, idempotent import и безопасный экспорт ячеек, начинающихся с формульных символов. CSV не исполняется как код. Нельзя импортом обойти запрет чужой организации.

Публичная аналитика — только разрешённые агрегаты и достаточные группы. Собственные продажи и клиенты — приватны. Фильтры, выгрузки и последовательные запросы не должны позволять восстановить чужой единичный заказ. Порог участников сам по себе не заменяет privacy review.

AI получает минимум данных; текст объявлений не становится инструкцией; никаких произвольных SQL/tools. Цены, действия и суммы окончательно проверяет сервер. Согласие на отправку сообщений/передачу внешнему обработчику и требования к хранению данных требуют проверки перед production.

## 8. Наблюдаемость и эксплуатация

Собирать request_id, ошибки API, задержку outbox, число retries, возраст последнего аналитического снимка, долю свежих предложений, нарушения остатков, расходы/latency LLM. Не записывать в логи полный секрет или личную переписку. FAQ не отправляет и не журналирует сообщения.

Backup БД, проверка восстановления, миграции с откатом/планом совместимости, отдельные demo/staging/production окружения. Демосброс запрещён для production. Нельзя обозначать резервную копию рабочей, не выполнив восстановительный тест.

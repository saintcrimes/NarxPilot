# Сервер NarxPilot

Домен: **narxpilot.software-engineer.online**. Установщик получает код из `https://github.com/saintcrimes/NarxPilot.git`, сохраняет секреты на сервере, собирает закреплённые зависимости и запускает Caddy, web, worker и отдельный PostgreSQL. По запросу владельца это публичный **демонстрационный стенд без браузерного пароля**. В приложении доступны демонстрационные профили покупателя/поставщика, регистрация и вход по паролю; данные синтетические. Для реальных организаций требуется отдельная production-конфигурация и проверка готовности к работе с реальными данными.

## Перед запуском

- Linux-сервер с root/sudo. При отсутствии Docker автоматическая установка поддерживает Ubuntu/Debian; другой Linux — с уже установленными Docker Engine, Compose 2.24+, Git, curl и util-linux.
- DNS A-запись `narxpilot.software-engineer.online` должна указывать на публичный IPv4 сервера. AAAA нужна только при реально доступном IPv6 этого сервера.
- В firewall/панели хостинга должны быть открыты входящие TCP 80 и 443; UDP 443 необязателен для HTTP/3. Порты должны быть свободны. Скрипт не отключает чужие Nginx/Apache и не меняет firewall.
- Серверу нужен исходящий HTTPS к GitHub, npm registry, Docker registry и центру сертификации. Для внешнего чата — к документированному Bro24 endpoint.
- Сборка выполняется на сервере: предусмотрите место под образы, PostgreSQL и резервные копии. Практический ориентир — 4 ГБ RAM и 20 ГБ свободного диска; минимальная конфигурация отдельно не измерялась.

## Одна команда

Запустите на сервере:

```bash
curl -fsSL https://raw.githubusercontent.com/saintcrimes/NarxPilot/main/deploy/install.sh | sudo bash
```

Код и серверный `.env` будут в `/opt/narxpilot`. Установщик создаёт случайные отдельные пароли БД/ролей/сессии; они остаются на сервере и не печатаются в журнал. После успеха откройте `https://narxpilot.software-engineer.online`: HTTP Basic Auth не используется, логин/пароль браузеру не нужны. Старые файлы доступа и переменные `DEPLOY_BASIC_*` от прежней установки могут оставаться на диске, но больше не используются и автоматически не удаляются.

HTTPS выдаётся и продлевается Caddy автоматически при правильном DNS и доступных портах; успешный внутренний healthcheck сам по себе не доказывает выпуск сертификата.

Для предварительного просмотра сохраните и прочитайте скрипт. `--dry-run` проверяет аргументы без сети и изменения системы:

```bash
curl -fsSL https://raw.githubusercontent.com/saintcrimes/NarxPilot/main/deploy/install.sh -o narxpilot-install.sh
bash narxpilot-install.sh --dry-run
sudo bash narxpilot-install.sh --domain narxpilot.software-engineer.online --dir /opt/narxpilot --ref main
```

`--ref` также принимает полный SHA проверенного коммита. Для воспроизводимого получения самого установщика замените `main` в download URL на тот же SHA. Скрипт не делает reset/force и не перезаписывает другую историю. Существующий каталог без этого Git-репозитория сохраняется и вызывает понятную ошибку; выберите другой `--dir`.

## API-ключ и настройки чата

Ваш локальный `.env` исключён из GitHub и Docker build context. Ключ с компьютера **не появляется на сервере при clone**. Основной продукт запускается без него. После установки добавьте ключ в серверный `.env` по SSH:

```bash
sudo nano /opt/narxpilot/.env
```

Параметры: `BRO24_API_KEY`, `BRO24_REPLY_JSON_PATH`, `CHATBOT_PROVIDER=bro24`, `CHATBOT_ENABLED=true`. Путь ответа нужно подтвердить по реальному ответу; имя поля не предполагается. Ключ нельзя помещать в `NEXT_PUBLIC_*`, командную строку, README или GitHub. Контекст NarxPilot в кабинете внешнего сервиса настраивается владельцем ключа; недокументированное поле контекста в запрос не добавляется.

Один диагностический запрос с безопасным вопросом:

```bash
sudo bash /opt/narxpilot/deploy/control.sh check-chat
```

Команда выводит HTTP-статус и возможные пути текстовых полей, без ключа, текста ответа или бизнес-данных. Она не меняет настройки автоматически. После подтверждения схемы включите provider и примените изменения:

```bash
sudo bash /opt/narxpilot/deploy/control.sh deploy
```

Не заменяйте всю серверную `.env` файлом с компьютера после первого запуска: уже созданная БД использует серверные пароли. Повтор installer сохраняет существующие ключи/пароли, обновляя явно заданный домен и HTTPS Origin. В `.local/deploy/` остаётся приватная копия изменённого `.env`. Если ключ не задан или формат не подтверждён, действует локальная справка; закупки и аналитика независимы.

## Управление

```bash
sudo bash /opt/narxpilot/deploy/control.sh status
sudo bash /opt/narxpilot/deploy/control.sh logs web
sudo bash /opt/narxpilot/deploy/control.sh logs worker
sudo bash /opt/narxpilot/deploy/control.sh logs caddy
sudo bash /opt/narxpilot/deploy/control.sh backup
sudo bash /opt/narxpilot/deploy/control.sh update
```

`update` проверяет чистый checkout и правильный origin, получает main и допускает только fast-forward. `.env` и `.local` игнорируются Git. Локальные изменения исходников останавливают обновление; они не удаляются. Свежая установка использует detached HEAD выбранного коммита, и `update` это поддерживает.

`deploy` сначала загружает и собирает образы, проверяет Caddy, затем запускает БД. Для существующей схемы создаётся `pg_dump` в `.local/backups/` и проверяется формат через `pg_restore --list`. Только после успешной резервной копии применяются миграции, права и идемпотентный demo seed. Затем обновляются web/worker/Caddy и проверяется их здоровье. Ошибка сборки не останавливает текущие сервисы; ошибка миграции не запускает новую web-версию. Полное восстановление backup нужно отдельно проверять в изолированной базе.

Данные хранятся в именованных volumes проекта `narxpilot-server`, включая PostgreSQL и сертификаты. Скрипты не выполняют `down -v`, удаление данных или автоматический откат миграций. Старые backups автоматически не удаляются: храните внешнюю копию и контролируйте место на диске.

## Проверка и ограничения

### Если миграция остановилась с EACCES /app/package.json

Первоначальные Dockerfile сохраняли root-владельца файлов checkout с правами `0600/0700`, созданных установщиком с `umask 077`. Поэтому непривилегированный пользователь контейнера не мог прочитать исходники. Исправленные образы назначают владельцем копируемых файлов пользователя приложения (`node` или `worker`); приватные права серверных файлов сохраняются.

Для уже созданной установки выполните:

```bash
sudo bash /opt/narxpilot/deploy/control.sh update
```

Команда получает исправления из main, пересобирает образы и повторяет миграции. Существующие `.env`, пароли и volumes сохраняются. Стандартный каталог установки — `/opt/narxpilot`, независимо от каталога, из которого вызван installer. При использовании `--dir` подставьте выбранный путь.

### Если status показывает только db

Установка ещё не завершена: для сайта нужны работающие `web`, `worker` и `caddy`. Сообщение `Valid configuration` проверяет Caddyfile в одноразовом контейнере, но не запускает HTTPS-сервис. Новый `status` показывает также остановленные контейнеры и перечисляет отсутствующие сервисы.

Скрипт выводит этапы `validate-caddy`, `start-db`, `inspect-db`, `migrate`, `start-app`, `start-proxy` и сообщает этап/код/строку при ошибке. Он не выводит `.env` или текст команды с секретами. Неинтерактивным Docker-командам явно отключён stdin; `pg_restore --list` получает только файл резервной копии. Это устраняет зависимость от ввода SSH-терминала при выполнении через `timeout`.

Для обновления существующей установки используйте закрытый stdin и сохраните код завершения:

```bash
sudo bash /opt/narxpilot/deploy/control.sh update </dev/null
printf 'DEPLOY_EXIT=%s\n' "$?"
```

Закрытый stdin применяется и к уже загруженным функциям старой версии `update`; новые функции доступны со следующего запуска скрипта. При повторной ошибке нужны последнее сообщение с этапом/кодом и `status`. Содержимое `.env` и файла паролей передавать не нужно.

### Azure: контейнеры healthy, но домен не открывается

Проверьте, что A-запись домена указывает на публичный IPv4 этой VM. В Azure откройте **Virtual machine → Networking → Network settings → Inbound port rules** и разрешите входящий **TCP 80 и 443**. Если NSG назначены и подсети, и сетевому интерфейсу, разрешение должно действовать на обоих уровнях. [Диагностика NSG в Microsoft Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem).

После изменения правил проверьте HTTPS. Если вместо таймаута появился `ERR_SSL_PROTOCOL_ERROR`, соединение уже достигает TLS, но нужен журнал Caddy: успешный admin-healthcheck не подтверждает наличие публичного сертификата. Если Caddy запускался при закрытых портах, после их открытия можно повторить получение сертификата перезапуском только прокси:

```bash
docker restart narxpilot-server-caddy-1
bash /opt/narxpilot/deploy/control.sh logs caddy
```

В журнале ищите результат получения сертификата или конкретную ошибку ACME. Ошибку сертификата исправляют на сервере; обход предупреждения браузера не требуется. Для проверки HTTPS непосредственно на VM, сохраняя проверку сертификата и правильное имя домена:

```bash
curl -I --max-time 15 --resolve narxpilot.software-engineer.online:443:127.0.0.1 https://narxpilot.software-engineer.online
```

Ожидаемый ответ готового публичного стенда — `200` без пароля и без `WWW-Authenticate`. При обновлении с прежней версии Caddy пересоздаётся с новым конфигурационным файлом; volumes сертификатов сохраняются. Если старое окно пароля уже открыто, закройте его кнопкой Cancel и обновите страницу после завершения deploy. `.env` с компьютера не попадает в GitHub: API-ключ добавляется в существующую серверную `/opt/narxpilot/.env`, с сохранением созданных паролей базы. Закупки и аналитика работают независимо от ключа Bro24.

### Границы проверок

Если `update` сообщает «Другой deploy/update/backup уже выполняется», существующий процесс держит блокировку. Для очередного обновления можно дождаться её освобождения одной командой:

```bash
flock /opt/narxpilot/.local/deploy-control.lock -c true && bash /opt/narxpilot/deploy/control.sh update </dev/null
```

Ожидание может быть без вывода. Запускайте эту команду один раз. Удаление lock-файла не завершает процесс и может разрешить конкурентные миграции. Активный процесс виден через `ps -eo pid,ppid,stat,etime,args | grep '[d]eploy/control.sh'`; полная команда его дочернего процесса — `ps -ww --ppid <PID> -o pid,etime,args`. `timeout 1800 ... build` означает активный этап сборки с пределом 30 минут. Работайте с исходным терминалом сборки, чтобы видеть её вывод.

Миграция 005 переводит видимый каталог на бакалею, сохраняя прежние SKU, заказы и события. Seed расширяет существующую демобазу, без удаления volumes. Подробнее: [GROCERIES.md](GROCERIES.md).

- Workflow `.github/workflows/validate.yml` создаёт настоящий lockfile при его отсутствии, выполняет тесты/типы/сборку и проверяет Docker-образы. Запуск CI не является деплоем на ваш сервер.
- `node --test deploy/tests/*.test.mjs` проверяет конфигурацию/секреты и Compose. `RUN_DOCKER_TESTS=true` дополнительно включает реальную проверку Caddy в контейнере.
- Bash-тесты проверяют аргументы и порядок/failure-сценарии через подставленные CLI, без изменения хоста.
- `bash deploy/tests/test-container-permissions.sh all` на Linux с Docker собирает оба образа из отдельной копии исходников с правами `0600/0700`, проверяет доступ к миграциям, запуск web и тесты под непривилегированными пользователями. Серверный `.env` в эту копию не включается. Эти проверки входят в CI.
- Полный Linux CI прошёл, включая настоящий Caddy, Compose и desktop/mobile E2E. В этом сеансе нет SSH-доступа к вашему серверу: DNS, выпуск сертификата, firewall и реальное восстановление БД там не проверены. Фактические результаты и число проверок — в [VERIFICATION.md](VERIFICATION.md).
- Автоустановка принимает только отдельную `narxpilot_demo` / `narxpilot_demo_*` базу. При live/test-конфигурации она останавливается, сохраняя файл. Подготовка production-среды для реальных организаций остаётся отдельной задачей.

Основа настройки: [официальная установка Docker для Ubuntu](https://docs.docker.com/engine/install/ubuntu/), [Debian](https://docs.docker.com/engine/install/debian/), [Caddy Automatic HTTPS](https://caddyserver.com/docs/automatic-https).
